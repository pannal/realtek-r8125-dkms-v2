# RTL8125 9.018 optimization baseline

## Direction

Use [awesometic/realtek-r8125-dkms](https://github.com/awesometic/realtek-r8125-dkms) as the **source baseline** for development, not the 9.014.01 code inherited from ewaldc. Keep `kernel-7-compat` as the historical 9.014 build-fix branch and use ewaldc only as a reference implementation.

## Findings from source review

- The awesometic 9.018.00 tree contains RSS machinery, multiple TX queue code, and MSI-X support but defaults to `ENABLE_RSS_SUPPORT = n` and `ENABLE_MULTIPLE_TX_QUEUE = n` in `src/Makefile`.
- The 9.014-based ewaldc code has these enabled and implements additional changes in queue, RSS, memory, and interrupt paths.
- A successful 9.014 module compilation on 7.0.0-38 established a Kbuild `EXTRA_CFLAGS` vs `ccflags-y` issue; this is a starting hypothesis for 9.018, not proof 9.018 builds unchanged.
- The 9.018 fork's DKMS packaging still uses `realtek-r8125-dkms` and module `r8125.ko`; it must **not** be co-installed with the current production package.

## Create the actual 9.018 source branch in a separate worktree

Run these commands **on a machine with GitHub network access**, from the existing clone:

```bash
cd /usr/local/src/realtek-r8125-dkms
git remote add realtek-9018 https://github.com/awesometic/realtek-r8125-dkms.git
git fetch realtek-9018 master
git worktree add -b realtek-9.018-optimized \
  /usr/local/src/realtek-r8125-9.018 realtek-9018/master
cd /usr/local/src/realtek-r8125-9.018
git push -u origin realtek-9.018-optimized
```

Do not run the above a second time if the remote, branch, or worktree already exists. Confirm `src/r8125.h` identifies version 9.018.00 and `git status --short` is clean before modifying the driver.

The separate worktree avoids replacing the locally checked-out 9.014 source or changing any installed module.

## First experimental steps

1. Record the exact baseline commit and hardware PCI revision.
2. Switch the 9.018 Kbuild compiler defines to `ccflags-y`, enable RSS and multiple TX queues in `src/Makefile`, and perform `make modules` **only** against the 7.0.0-38 headers.
3. Verify the generated module metadata and flags. Do not load/install it.
4. Inspect the differences against ewaldc's RSS hash/key/indirection management, RX buffer lifecycle, interrupt moderation, queue mapping, lock scope, TX completion, and page reuse. Forward-port narrowly.
5. Add a build-only CI workflow to the **new** branch, then test DKMS package behavior on an expendable host.
6. Before any production runtime swap, arrange independent console access and tested automated rollback. Measure throughput, missed RX packets, CPU cost, and interrupt distribution under repeatable load.

## Safety

Nothing in this plan authorizes `make install`, `dkms install`, `modprobe -r r8125`, or modifications to `eth0` on the production system.
