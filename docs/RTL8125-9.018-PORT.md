# RTL8125 9.018 optimized candidate: technical report

Status on 2026-10-18: source changes and local compile checks complete; hardware,
packaging lifecycle, hosted CI and recovery rehearsal remain unverified. This is
an experimental candidate, not a production-ready replacement or a measured
performance improvement. No production host was contacted or modified.

## Provenance and scope

The `realtek-9.018-optimized` branch starts at awesometic's 9.018 source,
[`9a152bf920334aead090d2fb4d91f67a84923123`](https://github.com/awesometic/realtek-r8125-dkms/tree/9a152bf920334aead090d2fb4d91f67a84923123).
The reference rewrite is ewaldc's 9.014,
[`527bcbe5ed45c67b20abae73dccc683eb6f0dc2b`](https://github.com/ewaldc/realtek-r8125-dkms/tree/527bcbe5ed45c67b20abae73dccc683eb6f0dc2b).
The target's older `master` and `kernel-7-compat` histories are preserved. Existing
port notes were read from `kernel-7-compat` commit
`f3f4b5b8298f12a6ef4fc69fda275b24ff9da725`; this report supersedes that plan on
the new branch without rewriting it.

Changes cover Kbuild defaults, selected queue/IRQ/NAPI/TX reliability paths,
compile tooling, legacy installer guards and documentation. PHY firmware,
Realtek hardware-method tables, DMA/page lifecycle, TX descriptors, offload
limits, interrupt moderation defaults, ASPM and EEE policies remain baseline.
No broad import from the older rewrite was used.

The reported target is Ubuntu 26.04.1, kernel 7.0.0-38-generic, PCI device
10ec:8125 with subsystem 1043:879b. This information and the historical
approximately 2.37 Gbit/s / zero-retransmission result are user-supplied, not
fresh hardware observations. Those IDs do not establish the silicon revision
or Realtek configuration method.

## Source comparison and decisions

Function references below refer to the pinned trees above. The relevant primary
files are [9.018 core](https://github.com/awesometic/realtek-r8125-dkms/blob/9a152bf920334aead090d2fb4d91f67a84923123/src/r8125_n.c),
[9.018 RSS](https://github.com/awesometic/realtek-r8125-dkms/blob/9a152bf920334aead090d2fb4d91f67a84923123/src/r8125_rss.c),
and [donor core](https://github.com/ewaldc/realtek-r8125-dkms/blob/527bcbe5ed45c67b20abae73dccc683eb6f0dc2b/src/r8125_n.c).
This is a focused path review, not a proof of the entire vendor driver.

| Area | 9.018 versus donor | Decision |
| --- | --- | --- |
| Queue initialization/mapping | 9.018 has per-ring descriptors/completion registers in `rtl8125_setup_mqs_reg`, active queue reporting through `rtl8125_set_real_num_queue`, and TX selection via `skb_get_queue_mapping`. It supports newer methods and up to eight RX/two TX queues; donor generally targets four RX/two TX. | Enable existing RSS and multiple-TX build paths. Preserve runtime hardware/ISR/vector gates; add RX queue recording before delivery to the stack. |
| RSS table and key | 9.018 uses a 128-entry table, validates supplied queue indices, packs key bytes explicitly, and supports RX descriptor types 3 and 4. Both trees can select three queues although hardware encodes `ilog2(count)`. | Retain newer table/key/descriptor handling. Round candidate queue counts down to a power of two so hardware queue encoding and default indirection agree. |
| MSI-X and IRQs | 9.018 supports ISR versions absent from donor, including ISR7. Its `rtl8125_try_msi` hides a negative fallback allocator result; donor's allocation path retains errors. Partial IRQ request unwind already exists in 9.018. | Propagate allocation failure to probe. Preserve vector maps, fallback, partial-request unwind and teardown. |
| RX reuse/memory | 9.018 already enables page reuse and stores separate `page`, CPU `data`, offset and DMA handle. Donor discards page metadata and uses `phys_to_page` / `phys_to_virt` with DMA addresses; its unmap path can use a page pointer rather than the original DMA handle. | Reject donor memory rewrite, especially with IOMMU/nonidentity DMA. Preserve 9.018 map/sync/unmap and page reference handling. |
| NAPI/moderation | Donor registers TX-only pollers with the TX NAPI API. It also hardcodes roughly 20 microseconds GRO timeout and 64 deferred IRQ polls. Both trees mishandle auxiliary poll completion. | Port dedicated TX registration on kernels >=6.1, preserving 9.018 ISR maps. Fix auxiliary zero-budget/completion handling. Leave moderation values unchanged pending latency/CPU measurements. |
| TX completion/locking | 9.018 already has subqueue stop/recheck barriers, `netdev_xmit_more` batching, GSO packet/byte accounting and a bound on hardware completion count. Donor's raw completion loop and accounting would regress these. | Retain current ordering and lock model; no speculative lock removal. |
| Offloads/error recovery | 9.018 bounds TCP header offsets, clamps MSS, retains chip-specific padding/LSO fixes, and unwinds fragment mapping before mapping the head. Donor has weaker checks and ambiguous first-fragment DMA failure reporting. Both retain padding ownership and checksum-error defects. | Keep newer offload/fragment/recovery logic; repair only padding ownership and software-checksum error propagation. |

## Implemented changes

1. `src/Makefile`: enable RSS and multiple TX queues, and emit feature defines
   directly through `ccflags-y` for every selected translation unit. Page reuse,
   NAPI, VLAN and DASH stay enabled. PTP remains optional and defaults off.
2. `rtl8125_init_software_variable`: constrain RSS ring count to a power of two,
   guarding zero/single-queue candidates before rounding. Existing vector checks
   and single-queue fallback remain in place. Three CPUs now select two queues;
   supported four/eight-queue configurations remain possible.
3. `rtl8125_try_msi`: preserve errors when both full MSI-X and single-vector
   fallback allocations fail. Probe now takes its existing cleanup path rather
   than pretending one interrupt exists.
4. `rtl8125_init_napi`: use `netif_napi_add_tx_weight` for dedicated TX callbacks
   on kernels >=6.1. RX/combined callbacks keep normal registration. TX vectors
   remain 16/18 for ISR2, 16/17 for ISR5 and 27/28 for ISR7.
5. `rtl8125_poll_msix_other`: do not complete or rearm on zero budget; report zero
   RX work and only rearm after successful NAPI completion. Kernel ownership of
   a deferred/busy-polled instance is respected.
6. `rtl8125_rx_skb`: record the actual receive queue before GRO/stack delivery.
   This improves queue provenance for stack consumers; it does not prove traffic
   distribution or install an XPS/IRQ-affinity policy.
7. Padding helpers: use `__skb_put_padto(..., false)` so the transmit error path
   remains the sole owner of the skb on allocation failure. The baseline helpers
   consume it on failure, followed by another free in `start_xmit`. Existing
   chip-specific padding selection and successful packet lengths are retained.
8. `rtl8125_tso_csum`: reject failed `skb_checksum_help` calls through the normal
   drop path instead of submitting a packet without a completed checksum.
9. Both default make targets compile only; the top-level legacy kernel selector
   no longer attempts to execute the kernel version as a shell command. Explicit
   inherited `make install` targets remain state-changing and must not be used
   for development or on production.
10. Legacy `autorun.sh`, `dkms-install.sh` and `dkms-remove.sh` now fail immediately
    without touching the system. In particular, the old autorun unloaded drivers
    before assuming `make all` installed the new module. The inherited publishing
    workflow is removed; the replacement workflow only builds/tests and retains
    uninstalled artifacts.

## Kernel compatibility and build evidence

The previous 9.014 Kbuild failure must not be generalized to current 9.018:
9.018 already contains `ccflags-y += $(EXTRA_CFLAGS)`. The untouched baseline
compiled against the exact 7.0 headers, including a separate build with RSS and
multiple TX enabled. No new Linux 7 API shim was needed. Direct `ccflags-y`
assignments remove legacy indirection and make selected features explicit.

Local builds used a disposable Ubuntu 26.04 userspace under an unprivileged user
namespace. Dependencies and headers were downloaded/extracted there; maintainer
scripts were not run and no host/production packages or modules were installed.
Older headers were tested in that same userspace, rather than claiming complete
Ubuntu 22.04/24.04 installations were exercised.

| Headers (amd64) | Compiler | Profile | Result |
| --- | --- | --- | --- |
| 5.15.0-199-generic, package 5.15.0-199.209 | GCC 11.5.0 | RSS, multiple TX, NAPI, page reuse, DASH | Linked and inspected |
| 6.8.0-147-generic, package 6.8.0-147.147 | GCC 13.4.0 | Same | Linked and inspected |
| 7.0.0-38-generic, package 7.0.0-38.38 | GCC 15.2.0 | Same | Linked and inspected |
| 7.0.0-38-generic, package 7.0.0-38.38 | GCC 15.2.0 | Same plus PTP | Linked and inspected |

The build script checks NAPI/RSS/multiple-TX/page-reuse/DASH defines in actual
compiler commands, RSS linkage (including Kbuild response-file inputs), optional
PTP linkage/defines, and module vermagic against the headers' configured release.
`modinfo` identifies the default candidate as `9.018.00-NAPI-DASH-RSS`, and the
PTP candidate as `9.018.00-NAPI-DASH-PTP-RSS`. Neither suffix proves runtime use.
Artifacts carry build logs, metadata and source/module hashes.

Kernel warning output includes compiler identity/version differences on older
headers and a tool-name-only warning for GCC 15 despite matching 15.2.0 builds.
BTF generation was skipped without `vmlinux`/pahole. No driver compilation error
was suppressed and no networking optimization was disabled to obtain a pass.

Six host-side regression tests compile actual extracted driver C with mocked
kernel services: IRQ allocation failures/fallback, RSS queue/table bounds,
auxiliary NAPI budget/completion, padding ownership, checksum failure, and NAPI registration mapping. All
six fail by executable assertions against the untouched baseline and pass on
this branch. These tests do not emulate the NIC or real allocation/DMA races.
Padding integration with the full TX error path was additionally traced manually.
Independent review also exercised actual NAPI registration across ISR1–7,
MSI-X enabled/disabled and all 32 vector indices.

`.github/workflows/build-only.yml` defines four configurations: rolling Ubuntu
22.04/24.04/26.04 GA headers, plus exact 7.0.0-38 with PTP. It runs host regressions,
compiles, inspects and uploads artifacts with read-only repository permissions.
It never installs or loads the driver. Hosted GitHub Actions execution remains
unverified because this branch has not been pushed. Exact pinned headers may
leave the archive in future; that job must fail visibly rather than silently
substitute a different target.

## Packaging and distribution recommendation

Use a dedicated **Launchpad PPA** for Ubuntu distribution after packaging and
runtime validation. A PPA hosts source-built Debian packages through APT; DKMS
then compiles the installed driver source for each local kernel. See
[Launchpad's PPA reference](https://ubuntu.com/docs/launchpad/user/reference/packaging/ppas/ppa/).
A signed self-hosted APT repository is an alternative if non-Ubuntu distribution
becomes necessary, but adds repository/key maintenance without a current need.

Recommended eventual identity: `realtek-r8125-optimized-dkms`, with a distinct
DKMS source registration and version such as `9.018.00+opt1`. Declare explicit
package conflicts with `realtek-r8125-dkms` and every other supported provider of
`r8125.ko`; determine that list during packaging validation. Only add `Replaces`
where actual file ownership/migration requires it. A distinct package makes the
switch opt-in; adding the PPA should not silently replace the installed stock
package. It does **not** make the modules co-installable. Avoid misleading
`Provides` relationships that imply the same validation/support guarantees.

The retained packaging is still upstream's, not the proposed packaging:

- `debian/control` names `realtek-r8125-dkms` and has no provider conflicts.
- `dkms.conf` registers `realtek-r8125/9.018.00`, installs `r8125` under updates,
  and enables autoinstall. It collides with the production registration/version.
- `debian/rules` copies sources to that same `/usr/src` identity. Source-only DKMS
  packages should be reviewed for `Architecture: all`, build dependencies,
  copyright/provenance, and unneeded `Multi-Arch: foreign` semantics.
- Custom postinst/prerm coexist with debhelper DKMS fragments. Review generated
  maintainer scripts for duplicated lifecycle work, upgrade/remove ordering,
  whether removal affects loaded modules and initramfs, and exact target version
  selection. Prefer one supported debhelper lifecycle after testing.
- The now-disabled helper scripts previously used `r8125` as the DKMS name while
  `dkms.conf` declared `realtek-r8125`; they were not a consistent migration path.
- PPA/archive signatures authenticate packages; they do not provide a kernel
  module signature trusted by Secure Boot. Test signing/MOK enrollment separately.

Before publication, build and inspect the source/binary packages in disposable
supported Ubuntu environments; test add/build/install, kernel update/autoinstall,
upgrade, remove, purge, stock-to-optimized migration and rollback. Verify package
conflicts prevent parallel providers, installed module selection matches intent,
and no source/build artifacts are shipped accidentally. Packaging success is
separate from module compilation and hardware acceptance. No `.deb`/source
package, PPA, release or repository upload has been created by this task.

For the production server, eventual installation means an explicitly approved
APT migration from the stock provider to the optimized provider, followed by
controlled activation through a tested independent console. Exact commands must
be prepared from the validated package and observed host state, not guessed now.
See [benchmark and rollback plan](BENCHMARK-AND-ROLLBACK.md).

## Outstanding validation and limits

- Confirm actual silicon revision/configuration method, queue/vector counts,
  interrupt delivery, RSS hash/indirection behavior and fallback operation.
- Existing CFG_METHOD_12 requests a minimum 49 vectors while its maximum and
  driver arrays are 32. Full-vector mode cannot succeed there; fallback remains.
  Do not expand arrays or invent vector layouts without CP-specific evidence.
- Kernel 5.15 retains ordinary TX NAPI registration under the >=6.1 guard. Very
  old kernels are outside the validated 5.15+ scope; legacy conditionals are not
  a compatibility promise. Only x86-64 compilation was checked.
- Run allocation/DMA fault injection on a disposable host; test IOMMU, memory
  pressure, fragmentation, small-packet flood, multiqueue stop/wake races, ring
  wrap, offloads, VLAN, jumbo frames and concurrent TX/RX.
- Test link loss/recovery, watchdog/reset, suspend/resume if supported, EEE/ASPM,
  shutdown/WOL and optional PTP on actual hardware. No production setting change
  is authorized by this report.
- Establish throughput, CPU cost, interrupt distribution, drops/retransmissions
  and latency with repeatable A/B runs. No gain over the reported 2.37 Gbit/s is
  claimed. Moderate interrupt rate alone is not proof of better performance.
- Out-of-band access and rollback must be tested before any production experiment.
  This task supplies a plan; it cannot claim that rehearsal occurred.

Independent review reproduced all four local build profiles and six regressions,
and found no remaining must-fix issue in the reviewed driver paths. Its installer
finding was addressed by disabling the legacy helper scripts. Runtime, packaging,
hosted CI and tested recovery remain explicit delivery limits.
